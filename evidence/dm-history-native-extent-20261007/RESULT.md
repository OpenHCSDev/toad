# DM paging uses committed message extent

The installed original mounted eight loading previews, interpreted their short boxes as the document extent and immediately admitted another forty rows. All mounted rows independently requested worker preparation. The original preview box cannot establish a source edge or sufficient scroll runway.

MountedMessageHistory now derives edge admission from each message's original body. IRC rows borrow WorkerStatic's completed current request, including a displayed preparation error; Markdown rows borrow their original body readiness. WorkerStatic publishes its original completion through the native message pump after layout. The history consumes that completion to reconsider demand. No readiness mirror, polling loop or new worker queue was added. Read acknowledgments remain painted-body facts, independently of settled extent.

One real private App workload with 140 persisted DM messages, the same current installed Core/Textual and no provider inputs:

| Observation | Original installed | Changed Toad source |
| --- | ---: | ---: |
| Rows admitted on open | 48 | 8 |
| Preparation submissions through one older page | 176 | 96 |
| Frames with visible loading previews | 92 | 33 |
| Opening all admitted text | 3088 ms | 2242 ms |
| Largest observed loop gap | 132 ms | 86 ms |

This is one headless pair, including cold worker startup. It does not prove terminal-pixel latency, live active-provider performance or that DM loading is fast enough. Each row still submits twice in this workload; that acquisition relation remains under investigation.

## Native width correction

The exact acquisition trace found every initial task was requested from a mount/style callback with zero widget width. WorkerStatic substituted App width 110, then native measurement supplied actual width 59 and discarded the first result. Preparation now waits for a positive native width instead of inventing it. The changed same workload submits 48 jobs for 48 admitted rows, all at width 59; eight opening rows are retained. Source run opening 2780 ms / one older page complete 3924 ms / largest loop gap 92 ms. Cold startup and loop stalls remain; no broad speed claim. Exact acquisition and changed results are `dm-acquisition-original/result.json` and `dm-admission-native-width/result.json` alongside the original artifacts.

The initial built extent-only successor also exercised the same real App and all modules loaded from its runtime: eight opening rows, 48 after an older page, 96 submissions and 20 preview frames; opening 3015 ms / largest loop gap 135 ms. This contradicts a reliable latency gain from the source pair alone. Its installed partial-viewport ACK/style-switch control passed. That intermediate build is preserved as evidence; the combined final successor is the delivery target.

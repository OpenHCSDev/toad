# Captured absolute motion

The original App waits for each routed pointer packet's DOM completion before reading the next packet. That ordering is necessary for press capture, release and Click ownership. It also made an absolute-position resize control replay every queued old width after the pointer had stopped. Dropping all MouseMoves would break drawing, selection and other ordered consumers.

The original MessagePump queue now asks its receiver `_can_replace_message`. Default behavior delegates the existing Message predicate. App admits only consecutive exact raw MouseMove packets from its original driver, with unchanged button/modifiers/prevention, no routed recipient, and no completion owner. It borrows current capture after the prior delivery completes and asks `Widget.can_replace_mouse_move(event, pending)`. Default False preserves FIFO. Parent owns the ResizeHandle override, whose primary drag depends on the absolute screen position and original starting width. No new queue, timer, motion state or global dropping.

Press/release, wheel, key, completion-owned packets, modified gesture inputs, subclasses and forwarded messages are barriers. The original capture resource and App/Screen routing acquire the actual final geometry; native selection, hit, frame/held-root, Click and cleanup owners are unchanged. Receiver permission explicitly includes intermediate positions/deltas/callbacks: arbitrary controls must not opt in merely because their final coordinates happen to match.
